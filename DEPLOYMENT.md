# Production-деплой через Dokploy

Это приложение — сервис на Next.js 16 с серверной формой сбора заявок. По умолчанию оно использует файл SQLite; на текущем этапе Postgres, Redis, SMTP, S3 и очереди не требуются.

## Модель деплоя

Используйте `Dockerfile` из репозитория в Dokploy. Он собирает standalone-версию Next.js и запускает её от непривилегированного пользователя `nextjs`. В данном случае это предпочтительнее Nixpacks: приложение использует нативный модуль `better-sqlite3` и нуждается в известном, воспроизводимом Linux-окружении сборки.

Контейнер принимает HTTP-запросы на `0.0.0.0:$PORT` (по умолчанию — `3000`). Не добавляйте `ports:` и отдельный сервис nginx/Traefik: приложение публикуется через Traefik, которым управляет Dokploy, — это единственная публичная точка входа HTTP(S).

## Переменные окружения

Создайте их в разделе **Environment** Dokploy. Не добавляйте файл `.env` с production-значениями в репозиторий.

| Переменная | Обязательна | Значение по умолчанию / рекомендуемое значение |
| --- | --- | --- |
| `PORT` | Нет | `3000`. Укажите этот же внутренний порт в Dokploy. |
| `LEADS_DB_PATH` | Нет | `/app/data/leads.db`. Рекомендуется задать явно, чтобы расположение данных было очевидным. |
| `NODE_ENV` | Нет | Образ уже устанавливает `production`; не переопределяйте. |

Секретов в приложении пока нет. Любая будущая переменная `NEXT_PUBLIC_*` встраивается в JavaScript браузера, поэтому в ней никогда не должно быть секрета. Учётные данные, доступные только серверу (для будущей CRM, SMTP или управляемой базы данных), храните исключительно в зашифрованных переменных окружения Dokploy.

## Постоянные данные и резервные копии

Добавьте persistent volume Dokploy, смонтированный в `/app/data`. В нём находится `leads.db` — SQLite-база с отправленными контактами. Volume обязателен: без него повторный деплой может привести к потере заявок.

Команды миграции базы пока нет: схема создаётся идемпотентно при старте приложения. Перед каждым релизом, который меняет схему, сделайте согласованную резервную копию SQLite при остановленной записи (например, временно уменьшив число реплик сервиса до нуля), затем скопируйте `leads.db` из volume в зашифрованное хранилище вне VPS. До того как полагаться на бэкап, проверьте восстановление на отдельном volume или сервисе. Для восстановления остановите приложение, замените файл базы в volume `/app/data` проверенной копией, убедитесь, что UID/GID контейнера `1001` может записывать в файл, затем снова запустите приложение.

SQLite подходит для этого лендинга в одном экземпляре. Не масштабируйте сервис до нескольких реплик, пока используется SQLite. Когда понадобятся конкурентная запись, отчётность или несколько реплик, перенесите данные в управляемый Postgres и передайте строку подключения через серверную переменную Dokploy. База должна оставаться во внутренней сети Dokploy; никогда не публикуйте её порт наружу.

## Чеклист первого деплоя в Dokploy

1. Добавьте VPS как **Remote Server → Deployment Server** и разрешите Dokploy Setup Server штатно установить Docker Swarm, Traefik и внутреннюю сеть. Подключение по SSH должно использовать ключ root; не включайте парольный SSH.
2. Создайте на этом сервере Application из Git-репозитория. Выберите тип сборки **Dockerfile** и `Dockerfile` в корне репозитория; Compose-файл не нужен.
3. Укажите внутренний порт приложения `3000`. Не публикуйте порты хоста вручную.
4. Добавьте persistent volume в `/app/data` и задайте `LEADS_DB_PATH=/app/data/leads.db`.
5. В разделе **Domains** добавьте production-домен, включите HTTPS/Let's Encrypt и направьте DNS-запись A/AAAA на VPS. Dokploy/Traefik направит домен на порт `3000`; второй reverse proxy не настраивайте.
6. Установите одну реплику и выполните деплой. Для малоресурсного VPS рекомендуем начать с **резерва 0,25 CPU / лимита 0,5 CPU** и **резерва 256 MiB RAM / лимита 512 MiB RAM**. Если образ собирается на VPS, оставьте не менее 1 GiB свободной памяти либо собирайте образ в CI и деплойте готовый.
7. Убедитесь, что Dokploy считает деплой здоровым, затем откройте `https://<ваш-домен>/api/health`. Ответ должен иметь статус HTTP `200` и тело `{"status":"ok"}`. Отправьте тестовую форму и убедитесь, что запись сохраняется после одного повторного деплоя.

Traefik публикует только порты 80/443; SSH остаётся отдельным административным портом. Docker API, файл SQLite, а также любые будущие сервисы данных и административные интерфейсы не должны быть доступны извне.

## Необязательный сценарий со сборкой образа в CI

Для малоресурсного VPS часто выгоднее собирать образ в CI: соберите этот Dockerfile под архитектуру VPS, присвойте каждому образу неизменяемый тег с SHA Git-коммита, отправьте его в приватный registry и настройте Dokploy на деплой именно этого тега. Так ресурсоёмкие сборки Next.js и нативного модуля выполняются не на VPS, при этом используется тот же Dockerfile. Не применяйте `latest`; сохраняйте предыдущий неизменяемый тег для быстрого отката.

## Локальная проверка production-сборки

```bash
docker build -t pilates-studio:local .
docker run --rm -d --name pilates-studio-check -p 3000:3000 \
  -v "$(pwd)/data:/app/data" -e LEADS_DB_PATH=/app/data/leads.db \
  pilates-studio:local
curl --fail http://127.0.0.1:3000/api/health
docker stop pilates-studio-check
```

Публикация порта хоста выше нужна только для локальной проверки и не является production-конфигурацией.
